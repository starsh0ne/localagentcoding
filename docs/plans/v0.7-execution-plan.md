# v0.7 执行方案：可观测性（结构化日志 + 成本/Token 核算）

> 状态：规划中（关键决策已由用户确认，2026-09-10）
> 关联：`docs/CHANGELOG.md` v0.7.0 条目

## 1. 已确认的关键决策（用户拍板）

| 决策点 | 选择 |
|--------|------|
| 范围 | 日志 + 成本账本（最小可用，满足生产 Tier-1） |
| 追踪后端 | LangSmith（**本次不做追踪**；该选择留作后续追踪版本的设计决策） |
| 成本/指标落地 | 仅结构化日志（不建 SQLite 账本、不暴露 `/metrics`） |

## 2. 目标

让本地运行的 agent-pro 在出问题时**可调试**、在烧钱时**可审计**，且不引入外部 SaaS 依赖。

## 3. 范围

**包含**
- 全链路结构化日志（JSON），覆盖 API 层 / Agent 层 / Worker。
- 每会话、每轮次（turn）的 token 用量与估算费用核算，作为结构化日志输出（含按模型拆分）。

**不包含（明确边界）**
- 调用链追踪 / span（tracing）——按决策本次不做；LangSmith 后端偏好已记录，待后续追踪版本。
- SQLite 成本库、Prometheus `/metrics` 端点、看板 UI——按决策不做。

## 4. 设计

### 4.1 日志框架（stdlib-only，零新依赖）
- 用 Python 标准 `logging`，自写 `JsonFormatter`（约 25 行，输出 `ts/level/logger/service/event` + 上下文字段），**不引入 `python-json-logger` 等新依赖**（保持离线/少依赖）。
- 输出双写：控制台(stdout) INFO 级 + 文件 `logs/agent_pro.log`（RotatingFileHandler，10MB×5，UTF-8）。
- 级别由 `config.LOG_LEVEL` 控制；`logs/` 加入 `.gitignore`（运行时产物）。
- 在 `observability/logging_setup.py` 提供 `setup_logging()`，于 API 入口(`api/__main__.py`/`server.py`)与 CLI(`main.py`) 各调用一次。

### 4.2 上下文字段注入
- 用 `contextvars` 持有 `session_id` / `turn_id` / `agent` / `model`；写一个 `ContextFilter` 把这些注入到每条 log record，全链路自动带上下文，无需每处手动传参。
- API 层每次请求生成 `request_id`(uuid) 写入 context。

### 4.3 成本核算（LangChain callback）
- 新建 `TokenUsageCallbackHandler(BaseCallbackHandler)`：
  - `on_llm_end` / `on_chat_model_end`：从 `response.usage_metadata` 或 `response_metadata["token_usage"]` 兼容读取 `prompt_tokens` / `completion_tokens`（LangChain 版本差异需兼容）。
  - 累加当前 run 的 token；run 结束时记一条结构化日志（model、session/turn、tokens、估算 cost）。
- 该 handler 作为**全局 callback** 挂到 agent 构造（`base.py`/`general.py`/`coder.py` 的 model/config 处），使通用 Agent 与 coder 两条链路自动覆盖。
- 价格表 `observability/pricing.py`：`MODEL_PRICING: dict[model, {"prompt": USD/1K, "completion": USD/1K}]`，初始填已用模型（LongCat / deepseek 等）公开价；未知模型退化为只记 token、不估费（避免误导）。`cost = (prompt+completion)/1000 * price`。
- turn 结束时，`worker.py` 汇总记一条 `cost_summary` 结构化日志（session_id, turn_id, total_prompt_tokens, total_completion_tokens, estimated_cost, by_model 拆分），供 grep/日志文件审计。

### 4.4 关键日志点
- API：`server.py` 每请求记 method/path/status/耗时；chat 提交记 session/turn。
- Agent：dispatch（通用→coder）记决策日志（为何 dispatch、目标 spec）；工具调用记 `tool_name`+耗时+成败。
- Worker：turn 生命周期(queued→running→done/error) + 累计 token/cost；异常记结构化 stack。

## 6. 实施步骤（建议顺序）

1. `logging_setup.py` + `JsonFormatter` + `ContextFilter`，`setup_logging()` 打通（先让服务起得来、出 JSON 日志）。
2. `config.py` 加 `LOG_LEVEL`/`LOG_DIR`，`.env.example`、`.gitignore` 跟进。
3. `cost.py`：`TokenUsageCallbackHandler` + `pricing.py`，挂到 agent 构造。
4. `worker.py` 在 turn 结束/异常处记 `cost_summary` 与结构化异常。
5. API/CLI 入口接入上下文字段（request_id / session / turn / agent / model）。
6. 冒烟验证（见 §7）。

## 7. 验证方式

- 起 API，发一条消息触发 dispatch→coder；检查 `logs/agent_pro.log`：
  - 有结构化 JSON 行（非纯文本）；
  - 含 `cost_summary` 与 token/estimated_cost；
  - dispatch/工具调用有决策与耗时日志。
- 不影响现有 SSE/鉴权/KB：用之前的 `curl` 流程回归一遍。
- 成本估算：对已知模型应出现估算值；未知模型仅记 token。
- 注意：本功能是**服务侧**日志，与「聊天面板可见 LLM 交互」(用户既有要求) 互补，不冲突。

## 8. 风险与注意

- LangChain `usage` 字段位置随版本变化，需兼容读取，否则 cost 记为 0。
- 长任务(曾 321s) 工具日志量大：INFO 级只摘要，全量留 DEBUG。
- 价格表会过时：在 `pricing.py` 顶部注释「需随厂商调价更新」，未知模型不估费。
